# 도쿄민박 패치 2 — 잔여 모순 제거 + 추천 기능 상담 전환 장치 강화

## 목표

지난 배포로 정리된 핵심 포지션을 기반으로, 남아 있는 잔여 모순을 제거하고 숙소 자동추천 기능을 "상담 전환 장치"로 더 명확하게 보이도록 개선한다.

---

## 절대 금지 사항

- 예약/결제/Beds24/webhook/cron 관련 코드 수정 금지
- ChannelTalk 연동 로직, 상담 컨텍스트 payload, 추천 결과 데이터 전달 구조 수정 금지
- DB 마이그레이션(`npm run db:migrate`) 실행 금지
- 확인되지 않은 정보(허가번호, 리뷰 출처, 운영자 정보 등) 임의 생성 금지
- 임시 하드코딩 금지
- 운영상 실제로 확인하지 않은 내용을 "확인했다", "검수했다", "보장한다"처럼 단정하는 표현 사용 금지

## 1. /recommend 페이지 문구 강화

### 제목

```
[현재] 도쿄 숙소 3곳 추천받기
[수정] 내 조건에 맞는 도쿄 숙소 3곳 추천받기
```

### 서브카피

```
일정·인원·희망 지역을 입력하면 조건에 맞는 후보 숙소 3곳을 먼저 확인할 수 있습니다.
최종 요금과 예약 가능 여부는 한국인 스태프가 숙소 운영자 또는 일본 현지 파트너와 확인 후 안내합니다.
```

### 추천 결과 안내 문구

추천 결과 상단 또는 결과 카드 근처에 추가:

```
추천 결과는 입력 조건을 바탕으로 한 후보 숙소입니다.
최종 요금, 예약 가능 여부, 체크인 조건, 취소·환불 조건은 상담 또는 예약 전 확인이 필요합니다.
```

### 상담 CTA

추천 결과 하단 CTA 문구:

```
이 3곳 기준으로 한국인 스태프에게 상담받기
```

**ChannelTalk 관련 주의:**
- 연동 로직, context payload, 데이터 전달 구조는 수정하지 않는다
- 기존 상담 메시지 템플릿이나 화면 문구가 있으면 **텍스트만** 아래 톤으로 수정:

  ```
  안녕하세요. 30초 숙소추천 결과를 보고 문의드립니다.
  최종 요금과 예약 가능 여부 확인 부탁드립니다.
  ```

- 일정/인원/희망 지역/추천 숙소 데이터가 실제로 자동 전달되지 않는다면, 해당 항목을 메시지에 하드코딩하거나 빈 값으로 노출하지 않는다
- 추천 조건과 추천 숙소 3곳을 ChannelTalk 상담 컨텍스트로 자동 전달하는 기능이 현재 없다면, 이번 패치에서 구현하지 말고 **TODO로 보고**한다

### 추천 결과 카드

가능한 범위에서 아래 요소가 보이도록 수정:

- 추천 이유
- 주의할 점
- 최종 확인 필요
- 한국어 안내 가능
- 상세 보기
- 이 숙소로 상담하기

**데이터 부족 시 규칙:**
추천 이유/주의할 점 생성에 실제 데이터가 부족한 경우, AI가 시설·가격·예약 가능 여부를 임의로 만들어내지 않는다.
데이터가 부족하면 아래 안전 문구만 사용:

```
입력 조건과 비교했을 때 후보로 추천되는 숙소입니다.
최종 요금과 예약 가능 여부는 상담을 통해 확인해 주세요.
```

## 2. 숙소 상세 자동 생성 문구 인원 모순 수정

`maxGuests` 값에 따라 문구가 정확히 분기되도록 수정한다.

### 분기 조건

```
maxGuests === 1:
  "최대 1명 기준이므로 1인 여행자에게 적합합니다. 2명 이상인 경우 다른 숙소를 함께 검토해 주세요."

maxGuests === 2:
  "최대 2명 기준이므로 1인 여행자 또는 2인 커플 여행에 적합합니다. 3명 이상인 경우 다른 숙소를 함께 검토해 주세요."

maxGuests >= 3:
  "최대 {maxGuests}명까지 이용 가능한 숙소입니다. 실제 이용 인원과 침대 구성, 공간 활용이 여행 스타일에 맞는지 예약 전 확인해 주세요."
```

### 주의

- `maxGuests`가 2 이하인 숙소에서 "3인", "2~3인", "소규모 3인" 등의 표현이 절대 나오지 않게 한다
- 자동 생성 SEO 문구, 상세 하단 안내 문구, 추천 대상 문구 등 관련 템플릿 전체를 검색해서 같은 문제가 남지 않도록 처리한다
- 기존 숙소 데이터나 예약 가능 인원 로직은 건드리지 않는다. **표시 문구만 수정한다**

## 5. 숙소 상세 '숙소 운영 정보' 섹션 구조 추가

숙소 상세 페이지에 향후 확장 가능한 섹션 구조를 추가한다.

### 섹션명

"숙소 운영 정보"

### 표시 가능한 필드

- 운영 유형
- 허가·신고번호
- 숙소 운영자
- 한국어 안내
- 후기 출처

### 표시 원칙

- DB나 API에 해당 데이터가 없으면 **섹션 전체를 숨긴다**
- 일부 필드만 있으면 있는 필드만 표시한다
- 확인되지 않은 정보를 임의로 만들지 않는다
- "확인 중", "미등록", "정보 없음" 같은 문구는 기본 노출하지 않는다

### 데이터 구조 처리 순서

1. 기존 `listing` 모델 또는 metadata/json 필드에 활용 가능한 구조가 있는지 먼저 확인한다
2. 있으면 그 구조를 활용한다
3. DB migration이 꼭 필요한 경우, **먼저 변경 범위와 리스크를 보고하고 별도 패치로 분리**한다
4. 임시 하드코딩은 금지한다

## 6. 리뷰 출처 표시 구조 점검

숙소 상세에 리뷰 수나 별점이 표시되는 경우, 출처를 표시할 수 있는 구조를 준비한다.

### 원칙

- 리뷰 출처가 명확하지 않은데 "도쿄민박 후기"처럼 단정하지 않는다
- 출처 데이터가 없으면 출처 문구를 숨긴다

### 출처 타입 예시

```
TOKYOMINBAK_REVIEW     → 도쿄민박 예약 후기
EXTERNAL_PLATFORM_REVIEW → 외부 플랫폼 후기
INFLUENCER_REVIEW      → 체험단 후기
HOST_PROVIDED_REVIEW   → 호스트 제공 후기
```

실제 구현은 현재 코드베이스의 타입/스키마를 확인한 뒤 가장 안전한 방식으로 진행한다.

- `게스트 대응은 호스트`
- `ゲスト対応はホスト様ご自身で実施`
- `2~3인 커플`
- `2~3인`
- `최대 2명 기준이므로 2~3인`
- `AI가 예약 가능한 숙소를 확정`
- `최저가 보장`

- `모든 숙소 직접 관리`

### 남겨도 되는 표현

- `한국어 1차 창구`
- `도쿄민박 한국어 안내 가능`

## 8. QA

### 로컬 체크

```bash
npm run lint
npm run build
```

### 확인 페이지

- `/`
- `/recommend`
- `/lp/host`
- 숙소 상세 2개 이상 (`maxGuests` 2 이하 1개, 3 이상 1개)

### 확인 항목

1. 메인 USP가 "예약 전후를 한국어로 안내하는 도쿄 현지 숙소" 또는 "한국어로 안내받을 수 있는 도쿄 현지 숙소"로 바뀌었는지

3. 추천 결과 안내 문구가 "후보 숙소 / 최종 확인 필요" 톤으로 표시되는지
4. `maxGuests` 2 이하 숙소에서 "2~3인" 문구가 사라졌는지
5. /lp/host에서 `ゲスト対応はホスト様ご自身で実施`가 사라졌는지
6. 숙소 상세에 "숙소 운영 정보" 섹션 구조가 추가되었고, 데이터 없을 때 노출되지 않는지

8. 예약 버튼·날짜 선택·인원 선택·가격 표시·결제 플로우에 영향 없는지
