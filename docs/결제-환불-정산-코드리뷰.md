## 2. 핵심 비즈니스 로직 검증 결과

### 2-1. 전액 환불(100% 취소) 로직

| 검증 항목 | 상태 | 설명 |
|-----------|------|------|
| 포트원 전액 취소 호출 | ✅ 적절 | 호스트 취소 시 `cancelPayment(paymentId, reason)`만 호출 → `amount` 미전달로 전액 취소. 게스트 취소 시 `refundRate === 1`이면 `refundKrw = paidTransaction.amount`로 전액 KRW 전달. |
| 정산/매출에서 수수료 0원 처리 | ⚠️ 설계상 만족 | 취소·환불된 예약은 `paymentStatus: "refunded"`, `status: "cancelled"`로 정산/매출 조회에서 제외됨. 따라서 “전액 취소 건은 매출에 포함되지 않음” → 수수료를 따로 0원으로 두는 별도 필드는 없으나, 결과적으로 전액 취소 건은 매출·정산에서 제외되어 수수료 부담 0원과 동일하게 동작함. |

**개선 제안 (선택):**  
전액 취소 시에도 `cancelPayment`에 `amount`를 명시적으로 넣어 두면 의도가 더 분명해짐. 현재처럼 생략해도 PortOne 기준 전액 취소로 처리됨.

---

### 2-2. 부분 환불(위약금 차감 후 취소) 로직

| 검증 항목 | 상태 | 설명 |
|-----------|------|------|
| 환불 금액 계산 | ✅ 적절 | `calculateRefundAmount()`(policies.ts)로 정책별 `rate`·`amount`(JPY) 계산 후, `refundKrw = round(paidTransaction.amount * refundRate)`로 **실제 결제액(KRW) 비율**을 적용해 포트원에 전달. |
| 포트원 API 전달 | ✅ 적절 | `cancelPayment(paymentId, reason, refundKrw)`로 `cancel_request_amount`에 해당하는 KRW 금액이 전달됨. |
| 부분 환불 후 정산/수익 계산 | ❌ 미구현 | 현재 정산·매출은 `paymentStatus: "paid"`, `status: "confirmed"`인 예약만 집계하며, **부분 환불된 예약(위약금만 호스트 수익)**은 “취소”로만 처리되어 정산 대상에서 완전 제외됨. “호스트가 가져가는 위약금”만 따로 합산하거나, 위약금에 대한 PG 수수료를 부과하는 로직은 없음. |

**정리:**  
- “게스트에게 돌려줄 금액” 계산 및 포트원 부분 취소 호출은 기획대로 동작함.  
- “부분 환불 건의 호스트 위약금 매출” 및 “위약금에 대한 PG 수수료” 반영은 현재 없음 → 기획 정책상 필요하면 별도 설계·구현 필요.

### 2-3. 웹훅 및 데이터 동기화

| 검증 항목 | 상태 | 설명 |
|-----------|------|------|
| 웹훅 수신·검증 | ❌ 취약 | `POST /api/webhooks/portone`에서 **요청 서명(시그니처) 검증이 없음**. PortOne에서 제공하는 웹훅 서명을 검증하지 않으면, URL이 노출될 경우 제3자가 위조 요청으로 결제/취소 상태를 바꿀 수 있음. |
| 결제 완료 금액 검증 | ❌ 오류 | `portonePayment.totalAmount !== booking.totalPrice` 비교 시, **totalAmount는 KRW(PG 결제 금액), totalPrice는 JPY(Booking 저장 통화)**라서 통화가 다름. JPY 환경에서는 거의 항상 불일치로 처리되어, 웹훅으로 들어온 결제 완료가 “금액 불일치”로 실패 처리될 수 있음. |
| 환불 후 DB 동기화 | ⚠️ 일부 이슈 | 우리 API로 환불 시: Booking `status: "cancelled"`, `paymentStatus: "refunded"` 갱신 + 환불용 `PaymentTransaction`(status `"refunded"`) 생성 → 적절함. 웹훅으로 취소 수신 시: 기존 `PaymentTransaction`만 `"cancelled"`로 업데이트하고, **환불 금액을 담은 별도 트랜잭션 레코드는 생성하지 않음** → 부분 취소가 웹훅으로만 들어오면 취소 금액이 DB에 남지 않음. |

## 3. 기타 발견 사항

### 3-1. PaymentTransaction.amount 통화 혼용

- **결제 완료 시:** `verify`에서 `portonePayment.totalAmount`(KRW)를 그대로 저장.
- **환불 트랜잭션 생성 시:** `refund/route.ts`에서 `amount: refundAmount` 저장. `refundAmount`는 `calculateRefundAmount`의 결과로 **JPY**.
- 따라서 한 건의 예약에서 “paid” 트랜잭션은 KRW, “refunded” 트랜잭션은 JPY로 저장되어, **통화가 혼재**함. 정산·리포트에서 합산 시 주의 필요.

### 3-2. PG 수수료(약 3.6%) 반영 여부

- 현재 매출·정산은 **Booking.totalPrice(JPY)** 합계만 사용하며, PG 수수료를 차감한 “정산 금액” 또는 “수수료” 필드는 없음.
- 전액 취소 시: 해당 건이 매출에서 제외되므로 수수료 0원과 동일.
- 부분 환불 시: “위약금만 매출”로 보는 로직과 “위약금에 대한 수수료” 계산이 없음.

## 4. 수정·보완 제안 (우선순위)

### 4-1. [필수] 웹훅 금액 검증: KRW vs JPY

**문제:** 웹훅에서 `totalAmount`(KRW)와 `booking.totalPrice`(JPY)를 직접 비교하고 있음.

**수정안:** `src/app/api/webhooks/portone/route.ts`에서 결제 완료(PAID) 처리 시, verify와 동일하게 “예상 KRW”를 계산한 뒤 비교.

```ts
// src/app/api/webhooks/portone/route.ts 상단에 유틸/환율 사용
import { getJpyToKrwRate } from "@/lib/exchange-rate";
import { STORED_CURRENCY, convertJpyToKrw } from "@/lib/currency";

// PAID 분기 내부:
if (portonePayment.status === "PAID" && booking.paymentStatus !== "paid") {
  const expectedKrw =
    STORED_CURRENCY === "JPY"
      ? convertJpyToKrw(booking.totalPrice, await getJpyToKrwRate())
      : booking.totalPrice;
  const paidKrw = portonePayment.totalAmount ?? 0;
  if (Math.abs(paidKrw - expectedKrw) > 1) {
    console.error(
      "Webhook: Amount mismatch paymentId=" + paymentId,
      "paidKrw=" + paidKrw,
      "expectedKrw=" + expectedKrw
    );
    await prisma.paymentTransaction.update({
      where: { id: transaction.id },
      data: {
        status: "failed",
        failReason: "Webhook amount mismatch (KRW)",
        rawResponse: JSON.stringify(portonePayment),
      },
    });
    return NextResponse.json({ ok: true, mismatch: true });
  }
  // ... 기존 트랜잭션·예약 업데이트
}
```

- `STORED_CURRENCY`가 JPY가 아닌 경우(예: KRW 저장)에는 위와 동일한 비교 로직을 그대로 쓰면 됨.

---

### 4-2. [권장] 웹훅 서명 검증

**문제:** 웹훅이 PortOne에서 온 요청인지 검증하지 않음.

**수정 방향:**  
PortOne 문서에서 안내하는 웹훅 서명 방식을 확인한 뒤, 예:

- 헤더에 담긴 시그니처와 `PORTONE_WEBHOOK_SECRET`(또는 문서에 명시된 비밀값)로 body 해시 검증.
- 검증 실패 시 `401`/`403` 반환하고 DB/상태 변경하지 않음.

(실제 헤더명·페이로드 형식은 PortOne 최신 문서를 따르면 됨.)

---

### 4-3. [권장] 환불 트랜잭션 amount 통화 통일

**문제:** paid 트랜잭션은 KRW, refunded 트랜잭션은 JPY로 저장됨.

**옵션 A – 모두 KRW로 저장 (PG 기준):**  
부분 환불 시 `PaymentTransaction` 생성 시 `amount`에 **실제 포트원에 요청한 환불 금액(KRW)**을 넣고, 필요 시 `currency: "KRW"` 같은 필드를 스키마에 추가해 구분.

**옵션 B – 현재 유지 + 문서화:**  
`PaymentTransaction.amount`의 의미를 “paid일 때는 결제 금액(KRW), refunded일 때는 환불 금액(JPY)”로 문서에 명시하고, 집계/리포트 시 `status`별로 통화를 구분해 사용.

---

### 4-4. [기획 연계] 부분 환불 건의 정산·수수료

- **정산:** 부분 환불된 예약에 대해 “호스트 위약금”(totalPrice - refundAmount)만 정산 대상으로 넣으려면,  
  - Booking에 `hostRetainedAmount`(또는 유사) 필드를 두고 환불 처리 시 갱신하거나,  
  - PaymentTransaction의 paid/refunded를 조합해 “실제 호스트 수익”을 계산하는 로직이 필요함.
- **PG 수수료:** “위약금에 대해서만 수수료 부과”를 반영하려면,  
  - 건별 수수료율(예: 3.6%)과 “정산 대상 금액”(전액 결제 건은 totalPrice, 부분 환불 건은 위약금)을 정의한 뒤,  
  - 정산/매출 API에서 “매출”, “PG 수수료”, “정산 금액”을 나누어 계산·노출하는 단계가 필요함.

위는 비즈니스 정책 확정 후 스키마/API 설계와 함께 진행하는 것이 좋음.
