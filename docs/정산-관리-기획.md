# 정산 관리 체계 기획

> 운영자가 수동으로 호스트에게 은행 입금(정산)을 하고, 해당 예약에 대한 정산 완료를 수동으로 체크하는 프로세스 기준

---

## 0. 마이그레이션 (구현 적용 시)

정산 필드 추가 마이그레이션:

```bash
npm run db:migrate
# 또는 DB가 PostgreSQL인 경우: npx prisma migrate deploy
```

마이그레이션 provider 불일치 시: `prisma/migrations` 의 `migration_lock.toml` 이 `sqlite` 인데 `schema.prisma` 가 `postgresql` 이면, [Prisma 문서](https://www.prisma.io/docs/guides/database/migrate-db-provider)에 따라 provider 전환 절차를 따르세요.  
또는 직접 SQL 실행:

```sql
ALTER TABLE "Booking" ADD COLUMN IF NOT EXISTS "settlementStatus" TEXT;
ALTER TABLE "Booking" ADD COLUMN IF NOT EXISTS "settlementAt" TIMESTAMP(3);
ALTER TABLE "Booking" ADD COLUMN IF NOT EXISTS "settlementNote" TEXT;
CREATE INDEX IF NOT EXISTS "Booking_settlementStatus_idx" ON "Booking"("settlementStatus");
```

---

## 1. 현재 구조 요약

- **Booking**: `status` (pending/confirmed/cancelled), `paymentStatus` (pending/paid/refunded/failed)
- **결제 흐름**: 게스트 결제 → 포트원 PG → `paymentStatus: paid` (PaymentTransaction 검증)
- **정산 관련**: 현재 별도 필드 없음. `paymentStatus: paid` + `status: confirmed` 인 예약이 호스트 매출로 집계됨

---

## 2. 정산 대상 및 조건

| 조건 | 정산 대상 여부 |
|------|----------------|
| `paymentStatus: paid` | ✅ 정산 대상 |
| `status: confirmed` | ✅ 정산 대상 |
| `status: cancelled` | ❌ 정산 제외 (취소 시 환불은 별도 프로세스) |
| `paymentStatus: refunded` | ❌ 정산 제외 |

**정산 시점**: 운영자 정책에 따라 결정 (예: 체크아웃 후 N일, 월 1회 일괄 등)

---

## 3. 데이터 모델 제안

### 3-1. Booking에 추가할 필드

```prisma
/// 정산 상태: null(미정산) | "pending"(정산대기) | "completed"(정산완료)
settlementStatus  String?  @default(null)

/// 정산 완료 시각 (운영자가 완료 체크한 시점)
settlementAt      DateTime?

/// 정산 처리 메모 (운영자 입력, 선택)
settlementNote    String?
```

### 3-2. (선택) Host 정산정보 테이블

호스트별 은행 정보를 별도 관리할 경우:

```prisma
model HostBankInfo {
  id            String   @id @default(cuid())
  userId        String   @unique  // 호스트
  bankName      String
  accountNumber String
  accountHolder String
  note          String?
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt
  user          User     @relation(...)
}
```

> 현 시점에서는 User 테이블에 `bankName`, `accountNumber`, `accountHolder` 등을 nullable로 두는 방식도 가능

## 4. 정산 프로세스 흐름

```
[게스트 결제 완료]
       │
       ▼
[Booking: paymentStatus=paid, status=confirmed]
       │
       ▼
[정산 대상 목록에 자동 포함]
       │
       ▼
[운영자] ① 정산 대상 예약 조회
        ② 호스트별로 그룹화 (또는 예약 단위)
        ③ 은행 이체 수행 (외부: 온라인뱅킹 등)
        ④ 시스템에서 "정산 완료" 체크
       │
       ▼
[Booking: settlementStatus=completed, settlementAt=now()]
```

## 5. 운영자용 정산 관리 화면

### 5-1. 정산 대시보드 (`/admin/settlement`)

| 영역 | 내용 |
|------|------|
| **요약 카드** | 미정산 예약 수, 미정산 총액, 이번 달 정산 완료 건수/금액 |
| **필터** | 기간, 호스트, 숙소, 정산상태(미정산/완료) |
| **정산 대상 목록** | 예약ID, 숙소명, 호스트, 체크인/아웃, 결제금액, 결제일, 정산상태 |
| **일괄 작업** | 선택 예약 다수 "정산 완료" 체크 |

### 5-2. 정산 상세/처리 화면

| 기능 | 설명 |
|------|------|
| **정산 완료 체크** | 해당 예약에 대해 "정산 완료" 버튼 클릭 → `settlementStatus=completed`, `settlementAt` 기록 |
| **메모** | `settlementNote` 입력 (이체 참조번호, 비고 등) |
| **호스트 은행정보 표시** | 정산 시 참고용 (마스킹 표시 권장) |

### 5-3. 호스트별 정산 요약 (추천)

- **그룹화 뷰**: 호스트별로 미정산 예약을 묶어 표시
- **호스트당 정산금액 합계** = Σ(해당 호스트의 미정산 예약 totalPrice)
- **일괄 완료**: 해당 호스트의 미정산 건을 한 번에 "정산 완료" 처리

## 6. API 설계

### 6-1. 정산 대상 조회

```
GET /api/admin/settlement
Query: startDate, endDate, hostId, listingId, status (pending|completed|all), page, limit
Response: { bookings, totalCount, summary: { pendingCount, pendingAmount, completedCount, completedAmount } }
```

### 6-2. 정산 완료 처리

```
PATCH /api/admin/settlement/[bookingId]
Body: { settlementStatus: "completed", settlementNote?: "이체완료 2024-02-15" }
```

### 6-3. 일괄 정산 완료

```
POST /api/admin/settlement/batch
Body: { bookingIds: [...], settlementNote?: "2월 1차 정산" }
```

## 7. 권한 및 보안

- **접근 권한**: `role: "admin"` 인 운영자만 정산 화면·API 접근
- **이력**: `settlementAt` 으로 완료 시각 기록 (감사 로그 확장 시 SettlementLog 테이블 추가 가능)
- **호스트 은행정보**: 마스킹 표시 (예: 110-***-******), 상세는 운영자 확인 시에만

## 8. 구현 단계 제안

### Phase 1 (최소)
1. `Booking` 에 `settlementStatus`, `settlementAt`, `settlementNote` 추가
2. `/admin/settlement` 페이지: 정산 대상 목록, 개별 "정산 완료" 버튼

### Phase 2
3. 기간/호스트/숙소 필터
4. 일괄 정산 완료
5. 요약 카드 (미정산 건수/금액, 완료 건수/금액)

### Phase 3
6. 호스트 은행정보 관리 (User 확장 또는 HostBankInfo)
7. 호스트별 그룹 뷰
8. CSV 내보내기 (정산 명세서)

## 9. 참고: 호스트 매출 vs 정산

| 구분 | 의미 |
|------|------|
| **호스트 매출** | 결제 완료된 예약의 `totalPrice` 합계 (이미 `/host/revenue` 에서 제공) |
| **정산** | 운영자가 실제로 호스트 계좌로 입금한 건에 대한 관리 |
| **미정산** | 매출은 발생했으나 아직 입금하지 않은 금액 |

호스트 입장에서는 "내 매출"을 보고, 운영자 입장에서는 "아직 정산 안 한 건"을 관리하는 구조.
